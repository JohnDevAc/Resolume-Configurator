**Actionable findings**

**R1 — P1: A complete component match still overrides a contradictory encoder identity.**

Location: [SourceMatcher.cs:51](<C:/Users/jligh/OneDrive/Documents/ChatGPT/Resolume Configurator/src/ResolumeConfigurator/Services/SourceMatcher.cs:51>); candidate components are flattened at [SourceMatcher.cs:13](<C:/Users/jligh/OneDrive/Documents/ChatGPT/Resolume Configurator/src/ResolumeConfigurator/Services/SourceMatcher.cs:13>) and any unique positive score can win.

Trigger: encoder `Hostname=TT-001`, `NdiChannelName=Main` is unavailable, while `TT-002 (Main)` is the only discovered candidate. The matcher chooses it. Conversely, `TT-001 (Preview)` is chosen even though the requested channel is `Main`. Matching one complete component is insufficient when the other known component contradicts the candidate. The numeric-prefix case fixed previously remains rejected.

Impact/evidence: the focused fixture reproduced both selections; the normal UI will label the returned candidate “Matched” and use its token for automatic placement. It can populate every affected layer with the wrong feed. NDI’s own naming contract distinguishes machine and source name in `MACHINE (source)`, so a common channel name is not a unique device identity. [NDI SDK sender documentation](https://docs.ndi.video/all/developing-with-ndi/sdk/ndi-send).

Smallest direction: retain typed host/channel components, reject contradictory known components, and require the complete available identity for automatic matching. Leave incomplete or conflicting candidates for explicit source selection. Owner: Resolume Configurator.

**R2 — P1: The restart helper accepts and saves a different composition with the same name and layout.**

Location: [PostRestartWorker.cs:82](<C:/Users/jligh/OneDrive/Documents/ChatGPT/Resolume Configurator/src/ResolumeConfigurator/Services/PostRestartWorker.cs:82>) accepts a matching name; [PostRestartWorker.cs:94](<C:/Users/jligh/OneDrive/Documents/ChatGPT/Resolume Configurator/src/ResolumeConfigurator/Services/PostRestartWorker.cs:94>) checks group/layer layout and column positions; [PostRestartWorker.cs:108](<C:/Users/jligh/OneDrive/Documents/ChatGPT/Resolume Configurator/src/ResolumeConfigurator/Services/PostRestartWorker.cs:108>) saves back over the requested file.

Trigger: during restart/loading, Arena exposes another graph named `Job`, with the same decoder/LED Wall/Show groups and three layers each, but different group, layer and clip IDs. The helper never reads the expected saved composition or compares its identities before restoration.

Impact/evidence: a real temporary `Job.avc` represented graph A. The mock API returned graph B with identical names/layout and different IDs. The existing `MatchesSavedStructure` correctly rejected B, but `RestoreCompositionAsync` still performed **15 guarded mock mutations** and replaced the saved file with B. Job/Agent revision checks cannot distinguish these two Arena graphs.

Smallest direction: load and pin the saved graph before restoration; require stable matching group/layer/clip identities using the existing synchronization comparator before any write. Recheck the relevant Arena identity during restoration if the operator changes compositions. Owner: Resolume Configurator.

**R3 — P2: Name-only preset reuse overwrites another sender’s occupied slot despite free capacity.**

Location: [KiloviewDecoderPresetService.cs:77](<C:/Users/jligh/OneDrive/Documents/ChatGPT/Resolume Configurator/src/ResolumeConfigurator/Services/KiloviewDecoderPresetService.cs:77>) and [KiloviewDecoderPresetService.cs:93](<C:/Users/jligh/OneDrive/Documents/ChatGPT/Resolume Configurator/src/ResolumeConfigurator/Services/KiloviewDecoderPresetService.cs:93>) reuse the first matching name without checking sender/ownership; N60 deletes that slot at [KiloviewDecoderPresetService.cs:202](<C:/Users/jligh/OneDrive/Documents/ChatGPT/Resolume Configurator/src/ResolumeConfigurator/Services/KiloviewDecoderPresetService.cs:202>).

Trigger: slot 1 is an existing `OTHER-PC (Arena - Decoder)` preset at `ndi://192.0.2.99:5961`, while the selected local sender is `192.0.2.10` and slot 2 is empty. Both family selectors reuse slot 1. A current discovery address check protects the new source, but does not prove ownership of the old slot.

Impact/evidence: the focused selector cases reproduced reuse for N6 and N60. A full `ConfigureAsync` run against an in-memory N60 transport emitted removal of the foreign-host slot, replaced and activated slot 1, and returned success while slot 2 remained available. No firmware was contacted. This can destroy an unrelated or fallback preset and contradicts the documented preservation of unrelated presets.

Smallest direction: retain and verify existing sender/managed-slot ownership before reuse. Prefer an empty slot when the matching label belongs to another sender; require explicit review before replacing a conflicting occupied slot. Owner: Resolume Configurator.

**R4 — P2: File patching and process restart bypass the fresh mutation guard.**

Location: [ArenaConfigurationOrchestrator.cs:179](<C:/Users/jligh/OneDrive/Documents/ChatGPT/Resolume Configurator/src/ResolumeConfigurator/Services/ArenaConfigurationOrchestrator.cs:179>) patches the AVC immediately after save completion without another guard. Both [ArenaCompositionSynchronizationService.cs:28](<C:/Users/jligh/OneDrive/Documents/ChatGPT/Resolume Configurator/src/ResolumeConfigurator/Services/ArenaCompositionSynchronizationService.cs:28>) and [ArenaRestartService.cs:22](<C:/Users/jligh/OneDrive/Documents/ChatGPT/Resolume Configurator/src/ResolumeConfigurator/Services/ArenaRestartService.cs:22>) invoke restart without a fresh job/Agent callback; [ArenaRestartService.cs:97](<C:/Users/jligh/OneDrive/Documents/ChatGPT/Resolume Configurator/src/ResolumeConfigurator/Services/ArenaRestartService.cs:97>) kills Arena.

Trigger: the selected job revision or PC identity changes while a save settles or while the synchronization API read is pending. HTTP writes will subsequently be rejected, but local file mutation or the process stop can already occur under stale authorization. The restart service checks process count/path, not job/Agent identity.

Impact/evidence: the fixture replayed the production Save → Patch → Update sequence using real save/patch methods and a mock HTTP transport. Revision drift was introduced after the save POST. The saved file was changed from 30 to 60 fps without a second guard; the following HTTP update then correctly rejected the changed revision. The process-restart paths were verified by source inspection only; no process was interrupted.

Smallest direction: pass the same pinned job/Agent validation callback through synchronization/restart and invoke it immediately before process interruption and explicit file mutations, including after awaited completion/read operations. Owner: Resolume Configurator.

**R5 — P2: Existing disabled Advanced Output mode is preserved when generated routing is committed.**

Location: [SimpleOutputConfigurationService.cs:20](<C:/Users/jligh/OneDrive/Documents/ChatGPT/Resolume Configurator/src/ResolumeConfigurator/Services/SimpleOutputConfigurationService.cs:20>) sets `advancedModeEnabled=1` only for a newly created document; existing documents retain their previous attribute. [ConfigurationFiles.cs:89](<C:/Users/jligh/OneDrive/Documents/ChatGPT/Resolume Configurator/src/ResolumeConfigurator/Services/ConfigurationFiles.cs:89>) stages this document for the configuration workflow.

Trigger: existing `SimpleOutput.xml` has `<SimpleSetup advancedModeEnabled="0">`. Configuration generates and commits new Advanced Output screens but leaves that explicit mode setting at zero.

Impact/evidence: the temporary-file Prepare → Commit fixture wrote valid generated output documents and retained `advancedModeEnabled="0"`. The persisted configuration therefore does not request activation of the advanced mode it just prepared. Arena’s documentation requires selecting Advanced Output to use those screens. [Resolume screens documentation](https://resolume.com/support/en/screens). The committed XML defect is reproduced; its live effect on sender publication needs the controlled hardware acceptance that was excluded here.

Smallest direction: explicitly set the intended Advanced Output mode on existing as well as new SimpleSetup documents and verify it together with the composition-sharing preference. Owner: Resolume Configurator.

**R6 — P2: The Job Configurator integration schema is ignored by the mutation eligibility checks.**

Location: [NdiJobConfiguratorReader.cs:85](<C:/Users/jligh/OneDrive/Documents/ChatGPT/Resolume Configurator/src/ResolumeConfigurator/Services/NdiJobConfiguratorReader.cs:85>) constructs identity from the three strings without checking `integrationSchemaVersion`; [JobRevisionGuard.cs:11](<C:/Users/jligh/OneDrive/Documents/ChatGPT/Resolume Configurator/src/ResolumeConfigurator/Services/JobRevisionGuard.cs:11>) compares only that identity.

Trigger: the selected endpoint serves valid-looking `serverId`, `jobId`, `jobRevision` and `devices` with a missing or unsupported integration schema. The suite contract explicitly defines public state schema 1, but the reader treats an unknown schema as compatible.

Impact/evidence: owned loopback endpoints returned missing schema and schema 99. Actual `ReadAsync` and `JobRevisionGuard.RefreshAsync` accepted both, and the guarded mock Arena mutation was dispatched once in each case. Schema 1 remained a positive control. The master independently reproduced missing/0/2 acceptance. No real server, Agent or Arena endpoint was used. This defeats fail-closed compatibility checks if a future/incompatible server changes identity semantics while retaining familiar fields; it is not a claim that the current schema-1 server is broken.

Smallest direction: require the supported numeric schema before constructing an actionable snapshot/identity, retain it as needed for revision comparisons, and show an upgrade/compatibility error for missing or unknown values. Owner: Resolume Configurator; the existing Job Configurator contract already supplies schema 1, so no server-side API addition is required.

**R7 — P2: Closing the main window abandons supervision of an active operation.**

Location: [MainWindow.xaml.cs:293](<C:/Users/jligh/OneDrive/Documents/ChatGPT/Resolume Configurator/src/ResolumeConfigurator/MainWindow.xaml.cs:293>) creates an operation-local cancellation source that is not connected to Closing/Closed; [App.xaml.cs:48](<C:/Users/jligh/OneDrive/Documents/ChatGPT/Resolume Configurator/src/ResolumeConfigurator/App.xaml.cs:48>) shuts down on main-window close. [ArenaRestartService.cs:27](<C:/Users/jligh/OneDrive/Documents/ChatGPT/Resolume Configurator/src/ResolumeConfigurator/Services/ArenaRestartService.cs:27>) launches an independent helper, and [WorkerCompletion.cs:23](<C:/Users/jligh/OneDrive/Documents/ChatGPT/Resolume Configurator/src/ResolumeConfigurator/Services/WorkerCompletion.cs:23>) stops it only when its monitored wait is cancelled/times out.

Trigger: the user closes the main window while Configure is busy or the helper is active. There is no operation-aware close handler, shared operation ownership lock, or parent-lifetime identity in the tracked helper request.

Impact/evidence: the unshown WPF fixture set both busy/helper flags and verified that `Close()` raises `Closed` without cancellation or blocking. Source inspection shows no close-to-operation cancellation or helper ownership transfer. In the initial phase the process can exit with partial work; after helper launch, the child can continue writes without the parent’s error reporting, and reopening permits another operation. Windows does not normally terminate children when their parent exits. [Microsoft process lifetime documentation](https://learn.microsoft.com/en-us/windows/win32/procthread/terminating-a-process). The helper’s own 15-minute deadline still applies; this is not an unbounded-worker claim.

Smallest direction: keep the UI alive until a safe stop/completion boundary or wire a coordinated cancellation/close path that waits for the owned helper and records the result. Prevent concurrent configuration against the same Arena instance across parent/helper/reopened instances. No live close/kill race was executed. Owner: Resolume Configurator.

**R8 — P2: A preference changed during the final guard is silently overwritten.**

Location: [ConfigurationFiles.cs:99](<C:/Users/jligh/OneDrive/Documents/ChatGPT/Resolume Configurator/src/ResolumeConfigurator/Services/ConfigurationFiles.cs:99>) compares all destinations with their originals before the commit loop, then [ConfigurationFiles.cs:107](<C:/Users/jligh/OneDrive/Documents/ChatGPT/Resolume Configurator/src/ResolumeConfigurator/Services/ConfigurationFiles.cs:107>) awaits validation for each file before writing at [ConfigurationFiles.cs:117](<C:/Users/jligh/OneDrive/Documents/ChatGPT/Resolume Configurator/src/ResolumeConfigurator/Services/ConfigurationFiles.cs:117>).

Trigger: Arena or another writer changes a preference after the initial batch comparison, while one of the potentially slow network/readiness checks is in progress. The current target is not compared again after its guard completes.

Impact/evidence: the fixture changed `SimpleOutput.xml` during the third validation callback, after the existing prechecks. Commit returned successfully and removed the new `userEdit` attribute. The changed document was captured in `simple.xml.original`, so manual recovery remains possible; this is a silent active-state overwrite, not an irrecoverable-loss claim.

Smallest direction: revalidate each destination against its pinned original immediately after the guard and use a replacement strategy that protects the remaining read/write interval, or detect the changed backup and stop/recover. Owner: Resolume Configurator.

**R9 — P2: Save verification assumes filesystem timestamps are at least as precise as the process clock.**

Location: [ResolumeApiClient.cs:162](<C:/Users/jligh/OneDrive/Documents/ChatGPT/Resolume Configurator/src/ResolumeConfigurator/Services/ResolumeApiClient.cs:162>) requires a changed file’s last-write timestamp to be greater than or equal to the high-resolution request-start timestamp.

Trigger: an otherwise valid custom/redirected output folder reports coarser write timestamps, or a share has timestamp skew. A new complete composition can have a last-write timestamp just before the in-process start value even though it was written after dispatch.

Impact/evidence: the fixture created a fresh parseable Composition after the mock save POST and rounded its timestamp down to a two-second boundary. Save verification timed out despite HTTP success and the fresh file; the precise-timestamp control succeeded. Microsoft documents two-second FAT write-time resolution and filesystem differences. [Microsoft file-time documentation](https://learn.microsoft.com/en-us/windows/win32/sysinfo/file-times). This was an emulated timestamp-precision test on temporary files, not a real FAT/SMB acceptance run.

Smallest direction: retain changed-file identity/content and settling checks, but account for the destination’s timestamp precision/skew instead of requiring exact ordering against the local high-resolution clock. Owner: Resolume Configurator.
